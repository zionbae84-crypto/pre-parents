# 다자녀/쌍둥이 옵션 + 날짜 입력 UX 개선 설계

## 배경

검색 폼에 "이 아이가 몇째인지", "쌍둥이(다태아)인지"를 입력할 방법이 없어서, 순위·다태아에 따라 금액이 달라지는 사업(강남구 출산양육지원금 등 약 15개)을 봐도 사용자가 자기 경우의 정확한 금액을 알 수 없다. 또한 검색 폼의 "출산완료" 상태에서 자녀 생년월일을 매번 입력해야 하는데, 이는 재검색할 때마다 반복 입력이 필요하고 "왜 날짜를 입력해야 하는지"에 대한 안내도 없다.

## 1. 날짜 입력 UX 개선

- **임신중**: 날짜 입력 위에 보이는 라벨 "출산예정일"을 추가한다 (현재는 `aria-label`만 있어 화면에 안 보임).
- **출산완료**: 생년월일 캘린더 입력을 없애고 "현재 개월수"를 숫자로 직접 입력받는다.
  - `lib/stage.ts`의 `UserStageInput`에서 `{ status: "born"; birthDate: string; today?: string }` → `{ status: "born"; childAgeMonths: number }`로 변경.
  - `determineStages`의 `born` 분기는 `calculateAgeInMonths(input.birthDate, input.today)` 대신 `input.childAgeMonths`를 직접 사용.
  - `calculateAgeInMonths` 함수는 이 변경 후 어디서도 호출되지 않으므로 함수와 관련 테스트를 제거한다 (죽은 코드 방지).
  - `app/search/page.tsx`의 `childAgeMonths = values.stageInput.status === "born" ? calculateAgeInMonths(values.stageInput.birthDate) : undefined` → `values.stageInput.status === "born" ? values.stageInput.childAgeMonths : undefined`로 단순화.
  - `SearchForm.tsx`: `birthDate` state를 `childAgeMonths` (number, 기본값 0)로 교체하고, "출산완료" 선택 시 `<input type="number" min={0}>` + 라벨 "현재 개월수"를 보여준다.

## 2. 다자녀/쌍둥이 입력 필드

검색 폼에 두 필드를 추가한다 (둘 다 매칭 필터링에는 쓰지 않는 정보성 입력):

- **"이 아이는 몇째인가요?"**: 숫자 입력, 기본값 1, `min={1}`.
- **"쌍둥이(다태아)인가요?"**: "단태아"/"쌍둥이 이상" 2단 필박스 버튼 (현재 상태 선택과 같은 스타일), 기본값 "단태아".

`SearchFormValues`에 `birthOrder: number`, `isMultipleBirth: boolean`을 추가하고, `SearchCriteria`(`lib/matching.ts`)에도 같은 이름으로 옵셔널 필드를 추가한다. **`matchProgram`의 판단 로직은 건드리지 않는다** — 이 두 값은 결과를 걸러내는 데 쓰이지 않고, 이미 매칭된 사업의 표시 내용을 보강하는 데만 쓰인다.

## 3. 데이터 모델

`SupportProgram`(`lib/schemas.ts`)에 선택 필드 3개를 추가한다:

```ts
birthOrderBenefit?: {
  tiers: { orderMin: number; amount: number }[]; // orderMin 오름차순. 마지막 tier는 "orderMin째 이상"에 적용
  flatAddOn?: number;               // 순위와 무관하게 항상 더해지는 고정액 (예: 성동구 현금 50만원)
  multipleBirthMode?: "sumConsecutiveOrders"; // 쌍둥이면 order, order+1 두 tier를 더해서 계산
};
multipleBirthFlatBenefit?: {
  singleAmount: number;
  multipleAmount: number;
  note?: string; // 계산에 쓰인 단순화 가정을 사용자에게 보여줄 문구 (예: "쌍둥이 2명 기준")
};
hasMultipleBirthOrOrderVariation?: boolean; // 위 두 구조로 정확한 금액 계산은 안 되지만, 다자녀/쌍둥이에 따라 내용이 달라지는 사업
```

세 필드 모두 옵셔널이며, 매칭 로직에는 관여하지 않고 표시 전용 계산에만 쓰인다.

### 계산 규칙 (`lib/birthOrderBenefit.ts`, 신규)

`calculatePersonalizedBenefit(program, { birthOrder, isMultipleBirth }): { amount: number; label: string } | { flagOnly: true } | null`

1. `birthOrderBenefit`이 있는 경우:
   - `tierLookup(order)` = `tiers` 중 `orderMin <= order`를 만족하는 항목 중 `orderMin`이 가장 큰 것의 `amount`. 없으면 0.
   - 단태아: `amount = tierLookup(birthOrder) + (flatAddOn ?? 0)`.
   - 쌍둥이 + `multipleBirthMode === "sumConsecutiveOrders"`: `amount = tierLookup(birthOrder) + tierLookup(birthOrder + 1) + (flatAddOn ?? 0)`.
   - 쌍둥이인데 `multipleBirthMode`가 없는 사업은 단태아와 동일하게 `tierLookup(birthOrder)`만 사용 (해당 사업엔 쌍둥이 특례가 없다는 뜻).
   - `amount <= 0`이면 `null` 반환 (해당 순위는 지원 대상이 아님 — 배지도 띄우지 않음).
2. `multipleBirthFlatBenefit`이 있는 경우: `isMultipleBirth`에 따라 `singleAmount`/`multipleAmount` 중 하나를 그대로 반환.
3. `hasMultipleBirthOrOrderVariation === true`인 경우: 금액 없이 `{ flagOnly: true }` 반환 (배지만 표시).
4. 셋 다 없으면 `null`.

`birthOrder`/`isMultipleBirth`가 검색에 입력되지 않은 경우(직접 링크로 상세페이지에 들어온 경우 등)에도 함수는 항상 호출 가능해야 하며, 입력이 없으면 `null`을 반환한다 (개인화 없음, 기존 화면과 동일).

## 4. 결과 표시

- **검색 결과 카드** (`ProgramCard`): `calculatePersonalizedBenefit` 결과가 금액이면 "OO째 자녀 기준 예상 혜택: OOO만원"을, `flagOnly`면 "다자녀/쌍둥이 조건에 따라 달라짐" 배지를 카테고리 뱃지 옆에 강조 표시. 결과가 `null`이면 지금과 동일하게 아무것도 추가하지 않는다.
- **상세 페이지** (`/programs/[id]`): 같은 계산을 더 눈에 띄는 박스(강조 카드)로 보여준다. 상세 페이지는 검색 없이 링크로 바로 들어올 수 있으므로, `ProgramCard`에서 상세 페이지로 링크할 때 `birthOrder`/`isMultipleBirth`를 쿼리 파라미터로 함께 전달한다: `/programs/[id]?birthOrder=2&multiple=true`. 상세 페이지는 `searchParams`에서 이 값을 읽어 동일한 함수로 계산한다. 쿼리 파라미터가 없으면(직접 방문) 개인화 없이 기존과 동일하게 렌더링된다.
- **적용 범위**: 이 개인화는 `/search` 결과 흐름에서만 나타난다. `/programs`(전체 목록), `/guide/[stage]`처럼 검색 조건이 없는 페이지의 `ProgramCard`에는 `birthOrder`/`isMultipleBirth`를 전달하지 않아 지금과 동일하게 보인다 (기존 `showEligibilityWarning`과 같은 옵트인 패턴).

## 영향받지 않는 범위

- `matchProgram`/`matchesRegion`/`matchesStage`/`matchesMotherAge`/`matchesChildAge`/`matchesIncome` 등 기존 매칭 로직은 변경하지 않는다.
- Bucket A/B/C에 속하지 않는 나머지 ~46개 사업 데이터는 변경하지 않는다.
- `/programs`, `/guide/[stage]` 페이지의 렌더링은 변경하지 않는다 (개인화 prop을 안 넘기므로 기존과 동일).

## 테스트 방침

- `lib/birthOrderBenefit.ts`: 순수 함수 단위 테스트 — tier lookup, `sumConsecutiveOrders` 합산(첫만남이용권 예시로 첫째+둘째=500만원 검증), `flatAddOn`, 지원 대상 아닌 순위에서 `null` 반환, `multipleBirthFlatBenefit` 단순 분기, `hasMultipleBirthOrOrderVariation` 플래그 분기.
- `lib/stage.ts`: `determineStages`의 `born` 분기가 `childAgeMonths`를 직접 사용하도록 테스트 갱신, `calculateAgeInMonths` 관련 테스트 제거.
- UI(폼 필드, 카드/상세페이지 표시)는 프로젝트 정책에 따라 자동화 테스트 없이 브라우저로 수동 검증한다.
