# 지역별 지원사업 데이터 리서치 워크플로우

이 문서는 `lib/data/programs.ts`에 지역(광역/기초자치단체) 임신·출산·육아 지원사업
데이터를 조사해서 반영할 때 따르는 표준 절차를 기록한다. 여러 지역(서울/경기/부산/
강원/인천/충북/충남/세종)을 거치며 겪은 실수와 교정 사항이 반영되어 있으니, **새 세션에서
이어서 작업할 때는 이 문서를 먼저 읽고 시작할 것.**

## 1. 전체 절차 (지역 하나를 새로 추가할 때)

1. **광역 전담 조사(province-wide agent)를 가장 먼저 실행**해서 "트랩 리스트"를 만든다:
   - 전국 공통 국비 사업(첫만남이용권, 부모급여, 아동수당 등 — 이미 반영되어 있음)
   - 진짜 광역(도/광역시) 전체 대상 사업
   - **"부분광역"(일부 시군에만 적용되는 광역 사업)** — 정확한 적용 대상 시군 목록까지 확보
   이 트랩 리스트를 다음 단계의 모든 시군구 조사 에이전트 프롬프트에 그대로 포함시켜서,
   시군구 에이전트가 이미 광역 차원에서 반영될 사업을 다시 "발견"해 중복 반영하는 것을 막는다.
2. **시군구를 3~5개씩 묶어 배치로 조사 에이전트를 병렬 디스패치**한다. 프롬프트에 반드시 포함:
   - 1단계에서 만든 트랩 리스트(제외 대상)
   - **"너 자신이 직접 WebSearch/WebFetch로 조사를 수행할 것. Agent(Task) 도구로 하위
     위임하지 말 것."** — 위임하는 에이전트가 실제 조사 없이 "곧 보고하겠다"는 빈 응답만
     반환한 사례가 있었음(인천 조사 때 발생).
   - 각 사업마다: 정확한 사업명, 금액(출생순위별 차등 있으면 순위별 정확한 금액), 지원대상,
     신청방법/기간, **공식 출처 URL(.go.kr)**, 확인일자를 모두 수집하도록 명시.
3. **에이전트 응답을 받는 즉시 원문 그대로 스크래치패드 md 파일에 저장**한다
   (`{scratchpad}/<region>-research.md`). 합성·요약하기 전에 먼저 저장 — 컨텍스트 압축으로
   유실되는 것을 막기 위한 핵심 안전장치. 실제로 이 저장을 건너뛰었다가 강원도 고성군·양양군
   조사 결과를 통째로 날려먹은 적이 있음(아래 3절 참고).
4. **웨이브 단위로 `lib/data/programs.ts`에 Edit**한다. 지역 블록 진입부에 표준 주석을 남긴다:
   ```typescript
   // ===== <지역명> =====
   // 출처: <기관> 공식 홈페이지(<domain>), YYYY-MM-DD 확인. [+ 제외/보류 항목 있으면 이유 명시]
   ```
5. **배치마다 검증 파이프라인 실행**:
   ```bash
   npx tsc --noEmit
   npx vitest run                       # 항상 전체 테스트 통과 확인(현재 83개)
   grep -c 'id: "' lib/data/programs.ts # 누적 총 건수 sanity check
   ```
6. **지역 전체 조사를 "완료"로 선언하기 전, 반드시 시군구별 커버리지를 grep으로 확인**한다:
   ```bash
   for s in 시군구1 시군구2 ...; do
     echo -n "$s: "; grep -c "sigungu: \"$s\"" lib/data/programs.ts
   done
   ```
   0건이 나오는 시군구가 하나라도 있으면 "조사는 했는데 파일에 반영을 안 한" 상태다.
   이건 실제로 강원도 고성군·양양군에서 발생한 사고였고(사용자가 "전부 조사가 완료된거야?
   빠짐없이"라고 재확인해서 발견됨), 이후 모든 지역에서 이 스텝을 마지막에 반드시 실행하는
   것으로 규칙화했다.
7. **커밋 → 푸시 → 배포 확인**:
   - 커밋 메시지는 한국어, `Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>` 포함.
   - `git push origin main` (이 프로젝트는 PR 없이 main 직푸시 워크플로우 — `gh` CLI 미설치 확인됨).
   - Monitor 도구로 배포 확인:
     ```bash
     until curl -s https://pre-parents.vercel.app/<path> | grep -q "<이번 배치의 특징적 문자열>"; do
       sleep 5
     done; echo "배포 확인됨"
     ```

## 2. 정보 누락 방지 로직 (가장 중요)

이 프로젝트에서 실제로 발생했던 누락 사고 두 가지가 지금의 규칙을 만들었다.

### 2-1. "조사는 했는데 파일에 안 쓴" 누락 — 시군구 단위
강원도 고성군·양양군을 분명히 조사했고 스크래치패드에도 데이터가 있었는데, 실제 `Edit` 호출을
빠뜨려서 `programs.ts`에는 0건으로 남아있었다. 사용자가 시군구 이름을 하나하나 나열하며
"빠짐없이 다 됐냐"고 재확인해서 발견했다.
→ **대응**: 1절 6단계의 `grep -c "sigungu: \"X\""` 전수 체크를 지역 완료 선언 전 필수 단계로
고정. 사용자가 재확인을 요청하지 않아도 스스로 이 체크를 항상 돌린다.

### 2-2. "광역 사업인데 일부 시군에만 적용되는" 누락 — 부분광역 패턴
충청북도 검토(`/review`) 때 발견: "임산부 교통비 지원사업"(8개 군 한정), "인구감소지역
4자녀 가정 지원사업"(6개 시군 한정) 둘 다 광역 조사 단계에서 정확한 금액·대상까지 확인은
됐는데, "광역 사업이니 한 번만 반영하면 되겠지"라고 판단해 개별 시군 항목으로 쪼개 넣는 걸
빠뜨렸다.
→ **대응**: 부분광역 사업은 **적용 대상 시군구마다 개별 entry를 하나씩** 만든다.
`agencyType: "광역"`, `agencyName: <도명>`, `region: { sido, sigungu: <해당 시군> }` 형태로
(경기도의 기존 패턴 `gg-paternity-leave-incentive-*`, `gg-birth-vulnerable-area-transportation-*`
참고). 이후 충남 조사부터는 광역 전담 에이전트에게 처음부터 "부분광역 패턴을 찾아라"라고
명시적으로 지시해서 사후 발견이 아니라 사전에 잡아내도록 했다.

### 2-3. 국가/광역/기초 중복 카운팅 방지
전국 공통 국비 사업(첫만남이용권, 부모급여, 아동수당 등)과 진짜 도 전체 대상 광역 사업은
시군구 레벨에서 다시 넣지 않는다. 이걸 위해 1절 1단계의 "트랩 리스트"를 항상 먼저 만들고
모든 시군구 조사 프롬프트에 포함시킨다.

### 2-4. 동일 사업이 여러 시군에서 "발견"되는 경우 — 광역 승격 판단
독립적으로 조사한 여러 시군 에이전트가 이름·금액·자격요건이 완전히 동일한 사업을 보고하면
(예: 충남 "다자녀 맘 건강관리 지원사업"이 서산/논산/당진/보령/청양/서천에서 토씨 하나
안 틀리고 동일하게 발견됨 — "2자녀 이상, 6개월 전부터 충남 거주, 최대 20만원"), 이는 사실
**광역(도) 사업 하나**이므로 시군마다 중복해서 넣지 않고 광역 레벨 entry 1개로 통합한다.

## 3. 정확한 정보 확인 로직 (신뢰도 관리)

### 3-1. officialLink 확보 우선순위 (fallback hierarchy)
1. 사업 내용을 직접 확인한 전용 상세 페이지 (`content-verified deep link`) — 최우선.
2. 살아있는 건 확인했지만 내용까지는 직접 확인 못한 전용 페이지(JS 렌더링 사이트 등) —
   `WebFetch`/`curl`이 내용을 못 긁어와도 페이지 자체는 200이고 제목/브레드크럼이 해당
   사업과 일치하면 사용 가능.
3. 그마저 없으면 시/군 홈페이지 대문(bare domain)에 코드 주석으로 "전용 페이지 미발견"
   캐비엇을 남기고 사용.
4. **위 어느 것도 없으면(홈페이지 레벨에서조차 근거 URL이 전혀 없으면) 그 항목은 아예
   반영하지 않는다.** 대신 지역 블록 상단 주석에 "제외 항목"으로 사업명·추정 금액·제외
   사유·문의 부서 전화번호를 남겨서, 다음 세션이 처음부터 다시 검색하지 않아도 되게 한다.
   (실제 사례: 충남 서천군 출산장려금, 홍성군 출산축하금/육아지원금/공공산후조리원감면 —
   조례 존재는 elis.go.kr/law.go.kr로 확인했지만 조문 본문이 JS 렌더링이라 금액을 못 읽어와
   2차 재검증 시도까지 실패, 주석에 재시도 이력까지 기록해 둠.)

### 3-2. 재검증(re-verification) 시 우선순위: 1차 출처
1차 정부 사이트가 직접 fetch로 안 열리면 다음을 시도한다(성공률 순):
1. `elis.go.kr`(자치법규정보시스템) — 조례 원문에 정확한 조문·금액이 있는 경우가 많다.
   `WebSearch`로 `"<지자체명> <사업명> 조례" elis.go.kr` 검색 후 `WebFetch`.
2. 지자체 보도자료 게시판(`<시군>.go.kr/cop/bbs/...selectBoardArticle.do?nttId=...`) —
   `site:<도메인> 보도자료 <키워드>`로 검색하거나, 게시판 검색 URL에 키워드를 넣어 `nttId`를
   추출한 뒤 개별 기사 URL로 재요청하면 JS 렌더링 문제를 우회해 원문을 얻을 수 있는 경우가 많다.
3. 그래도 안 되면 `curl -A "Mozilla/5.0" <URL>`로 직접 받아서 `sed 's/<[^>]*>/ /g'`로
   태그를 벗겨 텍스트만 grep — WebFetch가 실패해도 원문 HTML 자체에 데이터가 들어있는
   정적 페이지라면 이 방법으로 뚫린다(태안군 출산장려금 조례 확인에 사용).
4. 위 셋 다 실패하면 3-1의 4번(제외 + 주석 기록)으로 넘어간다. **절대로 언론 보도나 민간
   정리 사이트 숫자를 그대로 확정 반영하지 않는다** — 확인 시도 이력만 남긴다.

### 3-3. 스키마 상 정확도 표현 방법
- 출생순위별 차등 지급은 `benefit` 텍스트에 풀어 쓰는 것과 별개로 반드시
  `birthOrderBenefit.tiers`(`{orderMin, amount}[]`)로도 구조화한다 — 검색 결과 개인화
  계산 로직(`lib/birthOrderBenefit.ts`)이 이 필드를 사용한다.
- 특정 시점 이후 출생아부터 적용되는 개정 사항이 있으면(`예: 2023.1.1. 이후 출생아부터
  신규 단가 적용`) `eligibility.note`에 적용 기준일을 명시한다.
- `lastVerifiedAt`은 실제로 그 URL을 확인한 날짜를 쓴다(재검증했으면 재검증일로 갱신).

## 4. 특수 케이스 처리 패턴

### 4-1. 시군구 없는 단일 계층 광역자치단체 (세종특별자치시)
세종특별자치시는 기초자치단체가 없는 유일한 광역자치단체다. 처리 패턴:
- `lib/data/regions.ts`에 `{ sido: "세종특별자치시", sigungus: [] }`로 추가.
- 모든 자체 사업은 `agencyType: "광역"`, `agencyName: "세종특별자치시"`,
  `region: { sido: "세종특별자치시" }`(sigungu 필드 없음)로 등록.
- `lib/coverage.ts`의 `getCoveredSigungu`는 시군구가 있는 지역 전용이라 시군구 0개 지역은
  항상 커버리지 0으로 잡혀 헤더 뱃지가 안 뜬다 — 이를 위해 `hasSidoLevelProgram(sido)`
  헬퍼를 추가하고, `components/ui/Header.tsx`의 `RegionBadge`가 `total === 0`인 경우
  이 헬퍼로 뱃지 표시 여부를 판단하도록 분기 처리했다. **제주특별자치도도 이 패턴을 따라야
  하는지는 확인 필요** — 제주는 세종과 달리 제주시·서귀포시라는 하위 행정시가 있지만
  이들도 자치단체가 아닌 행정시(기초자치단체 아님)라 세종과 유사한 구조일 가능성이 높다.
  제주 조사 착수 전에 반드시 행정구역 구조부터 확인할 것.

### 4-2. 행정구역 개편이 진행 중/예정된 지역
인천광역시는 2026-07-01부로 중구·동구 폐지→제물포구·영종구 신설, 서구→서해구 개칭
(검단 지역은 검단구로 분리)라는 실제 개편이 있었다. 조사 도중 이를 발견해서
`regions.ts`를 개편 후 구조(9구 2군)로 맞추고, 이미 조사해둔 구 중구/동구 데이터를
제물포구로 재매핑하고 신설된 영종구·검단구는 별도로 새로 조사했다. **다른 지역도 착수
전에 최근 행정구역 변경 여부를 한 번 검색해서 확인하는 습관을 들일 것.**

## 5. 데이터 스키마 빠른 참고

- `lib/schemas.ts`: `SupportProgram` 정의. `agencyType: "정부"|"광역"|"기초"`,
  `region: "nationwide" | { sido, sigungu? }`, `stages: Stage[]`(임신준비/임신중/출생출산/
  영유아기/유아), `category`(현금지원/바우처/의료비/돌봄서비스/주거/세제혜택/기타),
  `eligibility`(motherAgeMin/Max, childAgeMonthsMin/Max, incomePercentMax, note),
  `officialLink`(zod `.url()` 검증됨 — 반드시 유효한 URL), `lastVerifiedAt`(YYYY-MM-DD),
  선택적 `birthOrderBenefit`.
- `id` 네이밍: kebab-case. 광역 사업은 지역 약어 접두사(`gg-`=경기도, `cb-`=충북, `cn-`=충남,
  `busan-`, `gangwon-`, `incheon-`, `sejong-`), 기초 사업은 로마자 시군명(`yesan-birth-grant`
  처럼).
- `lib/data/regions.ts`의 `RegionEntry[]`가 검색 폼 드롭다운과 헤더 뱃지의 유일한 진실
  소스다. 여기 추가하면 `lib/coverage.ts`가 `programs`에서 자동 집계하므로 다른 코드 수정은
  불필요(단, 4-1의 시군구 0개 케이스는 예외).
